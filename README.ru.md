# stadion

**Полигон для операционных решений.** Агента меряют против двух эталонов, с
которыми не поспоришь: классического метода исследования операций и точного
оптимума. На выходе нормированный счёт с доверительным интервалом, и
«неотличим от классического метода» здесь полноценный исход, а не погрешность
округления.

[English version](https://github.com/DrobyshevDev/stadion/blob/main/README.md)

---

## Зачем ещё один полигон

Среды, на которых сегодня учат и меряют агентов, — это код, браузеры и
SaaS-воркфлоу. У них общая беда: **никто не знает, каким был правильный ответ.**
61% на таком бенчмарке означает, что агент обыграл других агентов, а не что он
сработал хорошо.

στάδιον — это одновременно беговая дорожка и мера длины. Задачи здесь подобраны
так, чтобы быть и тем и другим. Каждая из них — решение, которое бизнес
принимает тысячи раз в день. У каждой есть учебниковый метод, к которому
потянется практик. И каждая достаточно мала, чтобы истинный оптимум можно было
вычислить обратной индукцией, а не приблизить.

Вот `examples/scarcity.py`: ставить цену выше, когда товара мало относительно
оставшегося времени, и ниже, когда он копится. Правильная форма, первое, что
приходит в голову, и очевидно лучше фиксированной цены.

```
pricing / scarcity
  instances        40
  agent               22.503
  classical           24.490
  optimum             26.006
  score               -1.310   (0 = classical, 1 = optimum;
                             one point = 1.516, 6.2% of the classical result)
  agent - classical: -1.987 [-3.038, -1.027] (-8.1%) -> worse
  agent - optimum: -3.503 [-4.403, -2.670] (-13.5%) -> worse
  optimum - classical: +1.516 [+1.265, +1.761] (+6.2%) -> better
```

Она проигрывает обычной фиксированной цене 8.1%, и интервал не задевает нуля.
На лидерборде против других адаптивных агентов она бы смотрелась прилично.

## Установка

```bash
pip install stadion-rl
```

Пакет для импорта — `stadion`, дистрибутив с суффиксом `-rl`, потому что имя
`stadion` на PyPI занято посторонним пакетом по каузальному моделированию.

## Как пользоваться

```python
import stadion

task = stadion.get("pricing")
report = stadion.evaluate(task, my_agent, instances=30, episodes=20)
print(report.summary())

report.score              # нормированный: 0 — классика, 1 — оптимум
report.vs_baseline.ci     # бутстрап-интервал на парной разности
report.degenerate         # True, когда классика уже оптимальна
```

У агента один метод:

```python
class MyAgent(stadion.Agent):
    name = "my-agent"

    def act(self, view: stadion.View) -> int:
        # view.text и view.choices  — то, что читает языковая модель
        # view.obs и view.env       — то, что читает численная политика
        return view.choices[0].value
```

Обе поверхности присутствуют всегда, поэтому RL-политику и LLM оценивают на
одной задаче, не переводя одну через интерфейс другой. Для языковой модели
`stadion.llm.LLMAgent` принимает любую функцию `prompt -> reply`: ни клиентской
библиотеки, ни провайдера.

### Прогон языковой модели

Эпизод — цепочка обращений: следующее решение нельзя начать, пока не известен
исход предыдущего, поэтому модель проводит оценку в ожидании, а не в счёте.
Инстансы друг от друга не зависят, значит их можно гнать разом.

```python
report = stadion.evaluate(task, lambda: LLMAgent(complete), instances=20, workers=8)
```

Больше одного воркера — и первым аргументом идёт фабрика, а не агент: агент,
который помнит что-либо внутри эпизода, между потоками не делится. Числа при
этом одни и те же, все сиды зафиксированы до старта пула.

Бюджет прогона считается в вызовах модели заранее. Один эпизод стоит одного
вызова на решение:

| Задача | Вызовов на эпизод | Меню |
|---|---:|---:|
| `queueing` | 100 | 2 |
| `inventory`, `energy`, `supply-chain` | 60 | 9, 9, 25 |
| `joint-pricing` | 40 | 48 |
| `pricing` | ~5 | 8 |

Один эпизод каждой задачи — около 325 вызовов, то есть прогон на восьми
инстансах по два эпизода по всем шести задачам обойдётся примерно в 5 200.

Из консоли:

```bash
stadion brief pricing --seed 3
```

```bash
stadion run inventory --agent optimum --instances 30
```

## Задачи

| Задача | Решение | Классический метод | Оптимум |
|---|---|---|---|
| `inventory` | сколько товара заказать за день при пуассоновском спросе | аналитический base-stock (критическая дробь newsvendor) | обратная индукция по остатку на складе |
| `pricing` | какую цену поставить в период при скоропортящемся товаре и дедлайне | сильнейшая фиксированная цена, подобранная перебором | обратная индукция по остатку товара |
| `queueing` | пускать заявку в буфер или отклонить | сильнейший фиксированный порог по ценности, подобранный перебором | обратная индукция с аналитическим интегралом по ценности заявки |
| `energy` | когда заряжать и разряжать батарею против суточного цикла цены | сильнейший фиксированный порог по цене, подобранный перебором | обратная индукция по решётке заряда |
| `supply-chain` | сколько заказать на двух звеньях за период до того, как заказ поможет | позвенный base-stock, подобранный перебором | обратная индукция по свёрнутому двумерному состоянию |
| `joint-pricing` | какую цену поставить и сколько дозаказать — одним решением | сильнейшая статичная пара «цена + уровень», подобранная совместно | обратная индукция по остатку на полке |

Среды и классические политики взяты из
[decisionrl](https://github.com/DrobyshevDev/decisionrl) без изменений, поэтому
соперник — тот же код, который эта библиотека выпускает и тестирует, а не
переписанная под проигрыш копия.

У последних двух действие непрерывное, и все игроки видят его как одно и то же
пронумерованное меню: девять уровней мощности для батареи, двадцать пять пар
заказов для цепочки. Вещественное действие классического правила привязывается к
ближайшему пункту меню, и его свободный параметр настраивается **через** эту
привязку — то есть под ту игру, в которую он на самом деле играет, а не под её
непрерывное послабление.

### Сколько в каждой места

Замерено на 40 инстансах по 20 эпизодов, воспроизводится командой
`stadion run <task> --agent classical --instances 40 --episodes 20`.

| Задача | Классика | Оптимум | Зазор | Интервал 95% |
|---|---:|---:|---:|---|
| `inventory` | 204.141 | 204.890 | **+0.4%** | [+0.561, +1.031] |
| `joint-pricing` | 110.099 | 114.812 | +4.3% | [+3.794, +5.656] |
| `pricing` | 24.490 | 26.006 | +6.2% | [+1.265, +1.761] |
| `queueing` | 21.911 | 25.611 | +16.9% | [+3.418, +3.988] |
| `supply-chain` | −37.532 | −31.027 | +17.3% | [+5.505, +7.493] |
| `energy` | 16.778 | 21.234 | **+26.6%** | [+4.221, +4.690] |

Разброс здесь и есть смысл. Пороговое правило по цене оставляет неиспользованной
четверть ценности батареи, потому что не умеет решить прийти к вечернему пику
заряженным. На другом конце формула newsvendor отстоит от точного оптимума на
полпроцента: на `inventory` выигрывать почти нечего, и агент, показавший там
крупное улучшение, нашёл баг, а не политику. Бенчмарк, у которого во всех
задачах щедрый зазор, молча отобрал те задачи, где классический ответ плох.

`joint-pricing` — случай, который поправил наши ожидания. Среда построена вокруг
связки: правильная цена зависит от того, сколько товара лежит на полке, поэтому
ни одна фиксированная цена не годится. Связка настоящая. В деньгах она стоит
4.3%: измеримо и заметно меньше, чем следует из формулировки «ни одно статичное
правило не годится». Число чувствительно к густоте ценового меню (2.2% на шести
ценах, 3.2% на восьми, 3.6% на двенадцати), поэтому меню поставлено там, где оно
почти перестало расти, а не там, где заголовок выглядит выигрышнее.

## Протокол

**Инстансы порождаются, а не хранятся.** `task.instance(seed)` вытягивает
уровень спроса, структуру издержек и горизонт из документированного
распределения. Числа, о которых спрашивают агента, не существовали до запуска,
поэтому запомнить их из публичного датасета нельзя.

**Агенту говорят всё, что говорят бейзлайну.** Бриф перечисляет параметры
инстанса полностью, потому что классическое правило строится из этих же
параметров. Скрыть их — не усложнить сравнение, а сделать его нечестным.

**Чего агент не получает, так это бюджета на настройку.** Там, где у
классического правила есть свободный параметр, он подбирается перебором на
тренировочных эпизодах, сиды которых никогда не встречаются в оценочном наборе.
Агент читает бриф один раз и играет. Ничья против настроенной классики — уже
результат.

**Всё парное.** Агент, бейзлайн и оптимум видят одни и те же инстансы и одни и
те же сиды эпизодов, а интервал считается бутстрапом по инстансам. Одна оговорка
названа прямо: пуассоновский сэмплер NumPy расходует переменное количество
случайных чисел, поэтому после первого расхождения политик расходятся и
траектории спроса. Парность снимает межинстансную дисперсию — крупное
слагаемое, — но не внутриэпизодный шум. Поэтому каждый инстанс усредняется по
нескольким эпизодам, прежде чем сравнивать плечи.

**Иногда потолок — это ничья.** На части семейств инстансов учебниковое правило
уже неотличимо от оптимума. Там у нормированного счёта нет знаменателя, и отчёт
так и говорит, вместо того чтобы поделить на маленькое число и показать
внушительную цифру. Бенчмарк, который это прячет, продаёт гонку, которую нельзя
выиграть.

## Проверка полигона против себя

Все числа здесь меряются **против** оптимума, поэтому обычный прогон не поймал
бы ошибку в рекуррентном соотношении. Ловит одна команда:

```bash
stadion verify
```

Она считает аналитическое значение динамического программирования и отдельно
симулирует политику, которую то же самое программирование выдало. Два
независимых пути к одному числу: они обязаны сойтись в пределах ошибки
Монте-Карло. Динамическое программирование, молча расходящееся с собственной
политикой, — та поломка, ради которой это написано, и проверка идёт в CI.

## Статус

v0.1: шесть задач, точные оптимумы, протокол оценки. На PyPI пока нет.

Это все прикладные среды `decisionrl`, и у каждой оптимум вычислен, а не оценён.
Следующая задача должна взять ту же планку, а большинство операционных задач её
не берут: как только в состоянии оказываются три непрерывных измерения, которые
не сворачиваются, потолок перестаёт быть фактом и становится мнением ещё одной
политики.

Issues и pull requests приветствуются.
